# Technical-Document Review

Review audience, structure, navigation, examples, and prose. This is not a technical-correctness verdict.

Check whether:

- the title, opening, scope, and prerequisites orient the intended reader
- the structure follows reader tasks or information needs rather than mirroring internals without reason
- concepts appear before dependent steps and detail is layered appropriately
- instructions, examples, API or reference sections, navigation, troubleshooting, and success checks appear where needed
- terms, interfaces, parameters, outputs, errors, constraints, and failure paths are explained consistently at the right depth
- code samples, tables, callouts, and diagrams clarify rather than interrupt or duplicate the text
- verified behaviour, assumptions, caveats, and unsupported promises are distinguishable
- links reach canonical detail without creating competing truth
- prose is clear, direct, appropriately technical, and free from avoidable jargon, unexplained acronyms, em dashes, and body-text boldface

Flag a technical claim as needing evidence when it appears unsupported, internally inconsistent, stale, or implausible, but do not declare it wrong without checking the authoritative source through technical evidence.

Return to the workflow report contract. State explicitly that the verdict covers reader fitness rather than correctness, and name any unresolved evidence question.
