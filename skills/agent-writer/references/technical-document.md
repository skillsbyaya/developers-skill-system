# Technical Document

Identify prerequisite knowledge, the reader task or decision, document type, scope, source of truth, and destination. Read the relevant current evidence; do not write technical specifics from general plausibility.

Organise task-led material by reader action rather than internal components. Use progressive detail: orientation and prerequisites before mechanics, then only the edge cases that affect safe use.

Include only useful sections, such as:

- verified steps, commands, or examples
- interfaces, parameters, requests, responses, errors, and limits
- constraints, failure modes, troubleshooting, and recovery
- reference tables or links to canonical detail
- verification or a clear definition of success

Keep examples small enough to understand and complete enough to use. Label code and data formats, state assumptions, and keep example outputs consistent with the evidence. Use a diagram only when it materially clarifies a relationship, sequence, state, or architecture shape and the destination supports an appropriate format.

Link to canonical material instead of copying it. Do not create competing reference truth.

For a standalone durable project document, use [the convention-resolution rules](../../organise-docs/references/convention-resolution.md) before saving and resolve the matching row. Do not load the conventions for an in-chat draft or a user-specified path. If no row fits, ask for the destination or choose a sensible location and report it.

Finish by checking prerequisites, steps, examples, links, failure handling, and success criteria against the source. Verify referenced paths or commands when the environment permits.
