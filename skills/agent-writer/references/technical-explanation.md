# Technical Explanation

Teach a concept, API, behaviour, or system well enough for a specific reader to understand or apply it.

1. Start from the reader's prior knowledge, question or pain point, and what they should be able to do afterwards.
2. Give a plain-language mental model tied to that goal before terminology or mechanics.
3. Layer detail from overview to mechanics to relevant edge cases. Avoid a taxonomy dump.
4. Use a concrete example or small code snippet when it makes the behaviour testable. Label illustrative values and evidence limits.
5. Use an analogy only when it clarifies the model, and map it back to the real system so its limits are visible.
6. Use a diagram only when relationships, sequence, or state are materially clearer in a supported visual format.
7. Close with common mistakes, checks, or the next useful action when the reader is likely to apply the explanation.

For a disputed or project-specific claim, inspect the authoritative source or preserve the uncertainty. Do not turn an illustrative explanation into an undocumented promise about system behaviour.

Finish by checking that the explanation starts at the reader's level, defines necessary terms, and makes the concept usable rather than merely familiar.
