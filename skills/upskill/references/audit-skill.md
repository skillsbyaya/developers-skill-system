# Audit a Skill

Use this route to judge whether a skill is fit for its intended outcome. Audit is findings work unless the user also authorises a change through the appropriate edit, repair, or restructure route.

## Choose the audit depth

- **Focused audit:** Use the procedure below for a narrow concern, ordinary review, or bounded evidence question.
- **Deep pressure test:** Read [Pressure-test a skill](pressure-test-skill.md) when the user asks for a thorough, adversarial, edge-case, or high-confidence review; when the audit is an acceptance gate for a new or materially redesigned skill; or when early evidence shows several interacting failures.

Do not select the deep route from file length or a general desire for confidence. A deep audit remains findings-only; return its proposed corrections through edit, repair, or restructure when the user authorises change.

## Establish the real job

State the recurring outcome, intended users, likely entry states, finished result, consequence, and neighbours before judging the file. Infer these from the request, skill, linked resources, consumers, and current environment. Ask only when an answer would materially change the conclusion or the safe fix.

Choose evidence for the concern. A narrow trigger question may need the description and adjacent descriptions; a procedure failure may need the selected route and a realistic walkthrough; a purpose or ownership concern may need neighbours, consumers, state, registrations, and system context. Do not make every audit an existence trial or library review.

## Judge fitness

Look for material failure in:

- natural triggering, explicit invocation, exclusions, and neighbouring boundaries;
- completeness and direct usefulness of the owned job;
- specialist judgement, evidence standards, failure handling, and finished-result checks;
- procedure reliability, exceptions, stop conditions, and adaptation to entry state;
- progressive loading, repeated reads, hidden prerequisites, and unjustified resources;
- mutation, approval, worker, state, document, and lifecycle authority;
- personal or project portability and current platform compatibility; and
- consumers, live frontmatter, links, and maintenance drift.

Distinguish a locally polished file from a systemically useful owner. Also distinguish high context cost from justified depth: remove or conditionalise material only when doing so preserves the decision quality and safeguards the outcome needs.

Read [platform compatibility](platform-compatibility.md) only when current Claude Code behaviour affects the finding. Read [registration and consumers](registration-and-consumers.md) only when metadata, routes, documents, generated views, or callers are in scope. Read [worker use](worker-use.md) only when worker design is in scope. Read [external skill discovery](external-evidence.md) only when requested or local evidence cannot resolve a material question.

## Report

Lead with consequential, evidence-backed findings. For each, name the affected outcome or realistic case, the cause, the impact, and the smallest change class that resolves it. Separate observation from inference and uncertainty. Do not manufacture a report, score, checklist record, or redesign when concise findings are enough.

If no material defect is supported, say so and name any meaningful evidence limit. Recommend edit for a known bounded correction, repair for a demonstrated failure class, or restructure only when ownership or purpose itself is the cause.
