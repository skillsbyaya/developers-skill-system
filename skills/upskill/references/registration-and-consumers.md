# Registration and Consumers

Read this reference when a skill is created, renamed, removed, nested, moved, or materially changes purpose, triggers, modes, saved information, documents, outputs, or ownership.

## Discover the local contract

Identify the authoritative skill location, installed names and frontmatter descriptions, document conventions, callers, routes, and current consumers that actually exist. Live frontmatter is the capability catalogue. Do not invent a declaration schema, generated registry, successor map, report, lineage record, mirror, or duplicate merely to demonstrate completeness.

When a skill is created, renamed, removed, nested, or materially changes purpose, triggers, or named modes, inspect the current frontmatter inventory and update the affected owners and consumers in the same change. Read only plausible neighbouring bodies when metadata cannot resolve the boundary.

Personal skills belong in the personal canonical root. Project skills belong to their repository and may depend only on declared repository context.

## Saved information and documents

Create a recurring output or saved information only when it improves later behavior, continuity, verification, reuse, maintenance, or recovery. Give it one owner, say who may update it and how to find it, and define when it should be removed or archived.

Put lasting project patterns, conventions, and constraints in the project's existing context source, preserving unrelated content. Do not put project-specific facts in global instructions, general memory, or output-only notes. `manage-project-context` owns creating or fully rebuilding that source; other skills may make only relevant, bounded updates.

Use the environment's authoritative document convention when one exists. Preserve a stable document contract through an ownership change only when the user's real workflow still needs it.

## Callers, routes, and lineage

Update direct callers, descriptions, named modes, links, permissions, templates, tools, and other affected parts of the system. For a removed or renamed capability, test the underlying user intent against the current owner's natural area trigger and direct modes. Fix a weak description or handoff when that route fails; do not retain a permanent alias, retired-name mapping, or duplicate owner to conceal the defect.

Keep lineage only in project-local evidence when it improves an active migration, maintenance decision, or recovery. Do not create mirror checks. If the environment requires another installed copy, update it as deployment work after the canonical skill is accepted; it is not design authority or a second source of truth.

Finish when the canonical skill, live frontmatter, document contracts, callers, routes, and links agree—or when a missing dependency is clearly named without creating duplicate truth.
