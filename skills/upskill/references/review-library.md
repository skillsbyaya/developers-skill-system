# Review the Skill Library

Use this route to assess coverage, ownership, routing, context, state, assurance, registration, and drift as one system. It is governance work, not a queue of individual audits.

## Start from work the system must enable

Derive material user goals, entry states, decisions, outputs, state transitions, quality needs, and credible failure surfaces without treating current skill names or categories as the required architecture. Build the current capability inventory from installed skill names and frontmatter descriptions, then use existing audits, runtime evidence, relationship data, and representative workflows before inspecting individual bodies.

Form focused hypotheses about:

- missing, duplicated, fragmented, or overloaded ownership;
- methods exposed as standalone skills despite sharing a natural area owner, or methods nested despite users entering through another area, no truthful parent, a misleading parent, required assurance independence, materially better cross-domain use, or materially better direct routing or total context;
- natural and explicit routing, neighbour ambiguity, and hidden preflight;
- common-route loading, repeated reads, handoff duplication, and maintenance cost;
- conflicting state writers, recurring documents without value or lifecycle, and generated views that compete with truth;
- risk controls that are missing or applied indiscriminately;
- stale consumers, descriptions, routes, links, and unsupported relationships; and
- mechanisms that would work better as ordinary reasoning, policy, a mode, reference, script, template, registry, tool, connector, or application.

Do not treat a method's specialist judgement, mutation, durable state, lifecycle, or high stakes as proof that it needs a separate owner. Test whether those responsibilities can remain complete inside one directly selected workflow under the natural area parent.

Inspect a skill deeply only when a concrete system hypothesis cannot be resolved from existing evidence. For suspected consolidation, compare the standalone route with an area-owner-plus-selected-workflow route, including discovery, loaded context, handoffs, authority, and direct explicit use. Walk representative outcomes and failure-prone routes instead of producing a scorecard for every skill.

## Use evidence proportionately

Treat uptake counts as evidence about opportunity and discoverability, never as automatic proof of value or deletion. Investigate substitution, consequence, frequency, discoverability, distinct value, and cost before recommending a change. Generate or retain an uptake report only when it has a current consumer and improves a decision; update the current report rather than accumulating history without a retrieval need.

Read [registration and consumers](registration-and-consumers.md) when checking metadata, generated views, document conventions, routes, or consumers. Read [worker use](worker-use.md) only if fresh independent judgement or safely isolated aggregation meets its criteria. Read [external skill discovery](external-evidence.md) only when the user requests outside comparison or local evidence cannot resolve a material system question.

## Boundaries and output

Library health owns system judgement and the lifecycle of skill-uptake evidence. Ordinary capability questions use normal reasoning over live frontmatter; deep context-cost diagnosis belongs to its token-optimisation owner; unresolved agent-behaviour lessons belong to the lessons owner; document conventions belong to the document owner. External skill discovery is a conditional `upskill` evidence route, not a prerequisite for library review.

Recommend focused owner or mechanism changes only when evidence shows how they improve material work. Separate observation, inference, preference, uncertainty, and required validation. Do not optimise toward a target count, create mandatory reports, or turn the review into a migration runbook.
