# Create a Skill

Use this route when the outcome is a new reusable capability. The requested filename, folder, or skill name is a proposal, not a settled mechanism.

## Derive the capability

Establish from available evidence:

- the recurring user outcome, users, likely inputs, finished result, and frequency;
- what becomes materially worse without reusable support;
- consequence, reversibility, uncertainty, and credible failure classes;
- durable preferences and environmental constraints; and
- realistic clear, vague, neighbouring, direct-method, and failure-prone requests.

Infer what the user and artifacts already settle. Ask only when a missing answer would materially change the mechanism, ownership, safety, or finished result.

## Choose the smallest reliable mechanism

Compare ordinary reasoning, an existing owner, a mode within an owner, global policy, a conditional reference, script, template, registry, tool, connector, application, and a new visible skill. Prefer the mechanism that makes the recurring outcome reliable with the least duplicated ownership and maintenance—not automatically the one with the fewest files or surfaces.

A new visible skill must own a recognisable user-facing job and add judgement or procedure ordinary reasoning would not supply reliably. A specialist method does not by itself justify a separate surface when it belongs to the same natural entry area as an existing owner.

Prefer a directly selectable conditional workflow when:

- users naturally enter through the same area owner;
- the parent can select the requested result without misrepresenting its area;
- an explicit method request can select it immediately without consultation or sibling-workflow preflight;
- only the selected workflow and required shared material load; and
- realistic routes show clearer discovery or lower total routing and context cost.

The workflow may own specialist judgement, mutation, durable records, and lifecycle rules. Retain or create a standalone owner only when the complete route proves that its authority must be independent of the plausible parent, such as when users naturally enter through another or several unrelated areas, no truthful parent exists without a vague umbrella, the parent would overclaim merely to route it, independent assessment must sit outside the producing area, or direct routing, cross-domain use, or representative total context is materially better standalone.

Do not accept “it has state,” “it mutates,” “it is high stakes,” “it is specialist,” or “it has its own lifecycle” as a conclusion. Do not create a skill solely for a tone, menu, preferred presentation, or sequence of other skills.

## Design the owner

Define:

- its direct job, natural triggers, exclusions, neighbours, and terminal outcome;
- the specialist judgement, evidence rules, failure handling, and verification it owns;
- whether one compact skill, an area owner with directly selectable conditional workflows, or an independent owner gives the clearest entry and authority boundary;
- which material is core, route-specific, deterministic, templated, or external;
- mutation, approval, state, document, and lifecycle authority;
- personal or project scope and portability; and
- consumers, live skill metadata, and routes affected by the new owner.

Before creating another owner, inspect the installed skill names and frontmatter descriptions, shortlist plausible neighbours, and read only the bodies needed to resolve ownership or overlap. Descriptions should translate the user's goal into the owner or named mode. An uncertain user may enter a compact domain owner; a knowledgeable user should be able to request a method directly. Never require a persona, planning step, or another skill as hidden preflight.

Read [platform compatibility](platform-compatibility.md) before choosing metadata, invocation controls, execution context, or structure. Read [registration and consumers](registration-and-consumers.md) for any installed skill. Read [worker use](worker-use.md) only if the design introduces or changes workers. Read [external skill discovery](external-evidence.md) only when comparison is requested or local evidence cannot answer a material design question.

## Author and prove the result

Write the smallest complete core and only the conditional resources that earn their cost. Give every supporting file an explicit loading condition. Prefer deterministic helpers for repeated fragile operations; test them against success and failure cases.

Validate current metadata and structure, parse frontmatter, resolve internal links and paths, and inspect affected callers and neighbouring live frontmatter. Walk the realistic cases derived above, including neighbour collisions and direct use without preliminary routing. For consequential skills, include adverse and incomplete-input cases and verify that controls follow actual risk rather than ceremony.

Before accepting any newly created skill, read [Pressure-test a skill](pressure-test-skill.md) and run its stages in order. Apply authorised in-scope corrections through this create route, rerun the affected stages, and stop if any material fitness doubt remains.

Complete only when the chosen mechanism materially improves the recurring outcome and the new owner fits the surrounding system without hidden prerequisites, duplicate truth, or unjustified maintenance.
