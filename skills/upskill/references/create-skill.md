# Create a Skill

1. **Confirm a skill is the right tool.** Most needs are better met elsewhere: ordinary reasoning (write nothing), a line in the user's global instructions (a standing preference), a section of an existing skill (same users, same starting point) or a script (a fragile mechanical sequence). Create a skill only for a recurring job that a capable model does noticeably worse without written guidance, and that the user would recognise as its own task. A tone, a menu or a fixed sequence of other skills is not enough.
2. **Check the neighbours.** Read the installed skill names and descriptions. If one already covers the area, extend it instead.
3. **Write the smallest version that works**, to the writing standard. Most skills fit in one `SKILL.md` under about 150 lines. Move material into a reference file only when it is large and needed on only some runs, and state when to read it. Use a script for any repeated fragile operation and test it on a success and a failure.
4. **Write the description once the body is settled.** Say what the skill does and when to use it, in the words the user actually says, third person, main use first. Add an exclusion only for a demonstrated collision with a neighbour's requests.
5. **Trial it.** Read the skill as the executing model against three realistic requests: a typical one, a vague one, and one meant for a neighbouring skill. When the skill deletes, deploys, changes data or spends money, add a failure case (missing input, a tool fails) and confirm it stops safely. When reading is not convincing, try a realistic task in a fresh session. Fix what the trial exposes, then ship as the core describes.
