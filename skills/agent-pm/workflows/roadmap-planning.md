# Roadmap Planning

Use the existing roadmap to review outcomes, scope trade-offs, milestone exits and sequencing policy. A review is read-only unless the user asks for updates. Create a roadmap only when requested and no current authority serves that purpose; follow project documentation conventions.

Read the roadmap's relevant rationale, current product decisions and the owning records for plausible work across areas. Distinguish:

- priority: which outcome matters more;
- preferred order: useful sequencing that need not block independent work;
- hard prerequisite: the named condition that must be satisfied;
- scheduled work: intended timing, not proof of milestone acceptance;
- milestone gate: a required exit condition linked to its acceptance owner and evidence.

Recommend sequencing from outcomes, evidence and constraints. An unblocked item is not automatically approved or highest priority. A required review remains an action with an owner; a merged change or finished chat does not prove that review or milestone acceptance occurred. Missing gate criteria remain unresolved, not inferred from elapsed time or scheduled completion.

For an authorised update, preserve strategic rationale and stable scope references. Apply settled decisions to affected stale questions and sequencing statements using the PM ownership rules. Keep current work status and next actions in their declared project sources and link them; do not create a second tracker in the roadmap. Partial adoption must say whether the candidate or adopted scope owns each affected milestone obligation.

When a prerequisite changes, identify dependent scope or evidence needing reassessment. Cancellation or supersession does not satisfy the old requirement. Leave unresolved scope and acceptance changes with their decision owner, and continue independent authorised work when possible.

Finish with the outcome or sequence changed, the reason, affected owners and any unresolved gate. Advice does not approve implementation or rewrite delivery lifecycle.
